# Резервная копия и восстановление PGlite

Эта процедура предназначена для **отдельного экземпляра** offix на Linux с PGlite и
файлами в одном каталоге данных: `pgdata/` и `uploads/`, включая `uploads/kusok/`,
если он используется. Она требует остановки всех процессов записи. Онлайн-копия
PGlite и копирование открытого kusok здесь не поддерживаются. PostgreSQL использует
другую процедуру; `deploy/linux/backup.sh` не является резервированием PGlite.

Ссылка жюри и свадебный сайт на общем сервере не являются тестовой площадкой:
эту инструкцию на них не запускать. Экземпляр для испытаний выбирается отдельно.

## Подготовка

1. Уточните настоящий каталог PGlite, uploads, расположение kusok, точное имя
   systemd-службы и всех других процессов, которые могут записывать данные. Если
   что-то расположено вне каталога данных, этот способ неполон: сначала подготовьте
   согласованную процедуру для всех хранилищ. Символические ссылки скрипт отклоняет.
2. Установите restic из доверенного источника на машине, где будет делаться копия.
   Подготовьте отдельный репозиторий вне каталога данных и желательно вне основного
   сервера. Ограничьте к нему доступ и храните ключ восстановления отдельно от сервера
   и копий. Не записывайте пароль в командную строку, Git или отчёты.
3. Обеспечьте управляемое окно обслуживания, запрет автозапуска и остановите все
   источники записи. Проверьте штатное завершение приложения в журнале, состояние
   службы и отсутствие других писателей. Если завершение было аварийным или
   принудительным, не объявляйте копию согласованной: отдельно проверьте базу и файлы.
   Скрипт проверяет состояние указанной службы, но не способен доказать, что она
   обслуживает выбранный каталог или что другие процессы не пишут в него.
4. Инициализируйте репозиторий один раз, заранее сохранив пароль. Пример с локальным
   репозиторием (для настоящего восстановления при потере машины нужна копия вне неё):

```bash
export RESTIC_REPOSITORY=/mnt/backup/offix-restic
export RESTIC_PASSWORD_FILE=/root/offix-restic-password
# Файл пароля создаётся отдельно в защищённом месте, доступ к нему — только ответственным.
chmod 600 "$RESTIC_PASSWORD_FILE"
restic init
```

Для удалённого репозитория предусмотрите отдельную учётную запись и проверьте
доступность восстановления с другой машины. Не храните ключи доступа в репозитории
проекта. Скрипт не меняет службы и не устанавливает таймеры.

## Создание копии

Только после остановки и проверки всех писателей:

```bash
export RESTIC_REPOSITORY=/mnt/backup/offix-restic
export RESTIC_PASSWORD_FILE=/root/offix-restic-password
bash deploy/linux/backup-pglite.sh example-offix.service /var/lib/example-offix
restic snapshots --tag offix-pglite-offline
restic check --read-data
```

Укажите реальные имя и путь **своего тестового экземпляра**; приведённые значения —
примеры. Сохраните идентификатор созданного снимка, время последней записи данных,
время копирования, SHA версии приложения и конфигурацию путей. Сверьте код выхода
каждой команды и сообщения об ошибках. Только после окончания копирования и проверок
возобновите работу экземпляра по его инструкции. Интервал с момента остановки записи
до следующей удачной копии и возможная потеря данных определяются фактическим
расписанием, а не самим наличием restic.

Копия чувствительна: в ней могут быть персональные данные и содержимое сообщений.
Пароли, ключи приложения, настройки окружения и двоичные файлы приложения **не входят**
в копию, если лежат вне указанного каталога; их нужно учитывать в отдельном защищённом
плане восстановления. Ключ шифрования копий хранить отдельно. Установите сроки
хранения, доступ и удаление с учётом требований организации; не запускайте
автоматическое удаление снимков до согласования этих правил.

## Проверка восстановления

Восстанавливайте конкретный идентификатор, а не предполагаемый последний снимок,
в новую пустую защищённую папку на изолированной машине без доступа к реальным
интеграциям. Команда не должна перезаписывать рабочие данные:

```bash
install -d -m 700 /tmp/offix-restore-check
# Убедиться, что папка действительно пуста; заменить SNAPSHOT на ID из snapshots.
restic restore SNAPSHOT --target /tmp/offix-restore-check
```

Restic сохраняет исходный абсолютный путь под `--target`: при исходном каталоге
`/var/lib/example-offix` результат находится в
`/tmp/offix-restore-check/var/lib/example-offix`. Проверьте владельца и права, а перед
запуском копии настройте отдельные порт, базу, хранилище, домен и отключение внешних
интеграций, почты и уведомлений. Проверить вход, созданную до копирования запись,
доступы двух ролей и выдачу вложения; сравнить SHA-256 с контрольной суммой, записанной
до копирования. Запишите измеренное время восстановления, версию приложения, объём
копии и время последнего сохранённого изменения. Не включайте реальные адреса,
содержимое или секреты в публичный протокол.

После проверки аккуратно удалите только изолированные временные данные в соответствии
с правилами хранения. Возврат в рабочую среду — отдельная операция с собственным
планом отката и согласованием владельца системы. Сам по себе `restic check` не
доказывает работоспособность приложения и корректность прав.

## Повторяемый технический тест

`deploy/linux/tests/recovery-check.sh` создаёт временные вымышленные данные в PGlite,
проверяет отклонение работающей службы, символической ссылки, неправильного пароля и
репозитория внутри данных; затем создаёт зашифрованную копию и восстанавливает файл.
Во второй части через API offix создаются вымышленные встреча и файл в чате. После
копирования и восстановления тест открывает базу и файловое хранилище в новом
процессе, проверяет встречу у участника и её отсутствие у постороннего, доступ к
файлу и совпадение SHA-256. Для изоляции тест подменяет проверку systemd и не
управляет настоящими службами. Файлы проверяются в режиме `fs`, не `kusok`.

Нужны `node`, `openssl`, `restic` и установленные зависимости проекта (`npm ci`):

```bash
export PGLITE_MODULE=/absolute/path/to/@electric-sql/pglite/dist/index.cjs
bash deploy/linux/tests/recovery-check.sh
```

Ключ для теста создаётся случайно во временной папке, которая удаляется после теста.
Тест не проверяет реальную службу, сетевое развёртывание, хранилище `kusok` или
восстановление после потери сервера. Для приёмки пилота нужны отдельный прогон на
изолированном экземпляре с реальным запуском службы, проверка kusok, если он
используется, учебная смена ключа и восстановление вне сервера. Запротоколируйте
измерения и ограничения; до выполнения не заявляйте, что эти проверки пройдены.
