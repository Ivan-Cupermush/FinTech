# SEC-01 — повторная проверка открытых соединений

## Гарантии и границы

HTTP проверяет подпись JWT, активность сотрудника, членство в организации и token_version на каждом обращении. Socket.IO раньше выполнял эту проверку при handshake. Маршруты смены пароля, отключения пользователя и завершения сеансов явно закрывают сокеты через disconnectUser. Отдельно требовалось закрыть соединение при истечении токена, отзыве версии другим процессом или изменении членства напрямую в базе.

Теперь открытый сокет повторно проверяется каждые 30 секунд. Между проверками проходит один интервал плюс время запроса к базе и задержка цикла событий. Это периодическая проверка, а не гарантия немедленного закрытия. Штатные действия через API по-прежнему вызывают немедленный disconnectUser. Во время недоступности базы соединение закрывается после ошибки проверки, пользователю требуется новое подключение.

События «печатает» и «перестал печатать» проверяют токен перед обработкой; выборка получателей ограничена текущей компанией и членством отправителя в чате. Ошибка запроса закрывает соединение. При закрытии таймер освобождается. Проверки одного сокета выполняются последовательно.

Роль HTTP читается из базы каждый раз. Маршруты рассылки по-прежнему отвечают за выбор допустимых получателей каждого содержательного события. Периодическая проверка сокета дополняет эти правила. При массовом росте числа подключений измерить нагрузку: на каждое соединение приходится до двух проверок в минуту. Общий токен в нескольких вкладках создаёт несколько проверок.

## Регрессионные проверки

server/test/socket-security.test.ts использует настоящий HTTP-сервер, Socket.IO-клиенты и PGlite с миграциями проекта. Проверяет:

- отзыв token_version закрывает соединение, прежний токен получает HTTP 401 и отказ повторного handshake, новый токен работает;
- отключение пользователя закрывает две вкладки, соединение другого сотрудника продолжает работать;
- удаление членства закрывает открытый сокет;
- истечение подписанного токена закрывает поток без действий клиента;
- при сбое проверки базы соединение закрывается, после восстановления можно войти заново;
- действующий участник продолжает отправлять индикатор набора текста другому участнику чата.

Тесты используют интервал 100 мс. Он ускоряет проверку поведения и не измеряет срок доставки в промышленной конфигурации. Дополнительно проверить прежние сценарии test/chats.test.ts, test/security.test.ts, test/account.test.ts и test/org-auth.test.ts.

## Сценарий для жюри

На отдельном пилотном наборе открыть чат в двух вкладках сотрудника и одной вкладке руководителя. Руководитель отключает сотрудника штатной операцией. Продемонстрировать закрытие обеих вкладок сотрудника и отказ старого токена при повторном обращении. Вернуть сотруднику доступ, выполнить новый вход и показать нормальную переписку.

Периодическую проверку отдельно демонстрировать на стенде для испытаний, воспроизводя отзыв версии вне маршрута API. Протокол содержит SHA, время изменения и время disconnect. Для реального интервала 30 секунд повторить несколько раз, включая изменение сразу после удачной проверки. До такого прогона в материалах указывать механизм и настройку, без заявления об измеренном промышленном времени.
