# Устройство kusok

## Модули

```
include/kusok/kusok.h   публичный API
src/
  bytes.h      чтение/запись чисел little/big-endian
  sha256.c     SHA-256: переносимая версия + SHA-NI (выбор при запуске)
  crc32c.c     CRC32C: slicing-by-8 + инструкция SSE4.2 crc32
  cdc.c        FastCDC: gear-хеш, нормализованная нарезка, потоковый режем
  lz.c         сжатие/распаковка в формате блока LZ4, быстрый режим и HC
  tab.c        хеш-таблица с открытой адресацией (ключ — 32 байта id)
  fsutil.c     pwrite/pread до конца, fsync каталога, атомарная запись
  pack.c       pack-файлы: заголовок, записи, проверка, обход
  manifest.c   манифест файла: список кусков, поиск по смещению
  journal.c    журнал счётчиков ссылок + снимок
  pool.c       пул потоков: parallel-for по номерам задач
  idx.c        файл .idx рядом с закрытым pack: заголовки всех записей
  cache.c      LRU-кэш распакованных кусков
  bundle.c     export/import пакетов для бэкапа
  store.c      само хранилище: открытие, запись, чтение, ссылки
  gc.c         сборка мусора
  fsck.c       полная проверка
tools/kusok.c  командная строка
tools/http.c   разбор HTTP/1.1: строка запроса, заголовки, Range
tools/serve.c  сервер на poll(): соединения, конвейер, ответы
bindings/node/ привязка N-API: класс Kusok, промисы через пул libuv
tools/bench.c  бенчмарк и эксперименты с дедупликацией
```

Зависимости строго сверху вниз: примитивы (`sha256`, `crc32c`, `cdc`, `lz`,
`tab`, `pool`, `cache`) ничего не знают о диске, форматы (`pack`, `manifest`, `journal`)
ничего не знают о хранилище, а `store`/`gc`/`fsck`/`bundle` собирают всё
вместе. HTTP живёт в `tools/` и пользуется только публичным API.
Каждый модуль тестируется отдельно.

## Как файл попадает в хранилище

1. Поток байт идёт в чанкер (`ks_chunker`). Он держит буфер в два
   максимальных куска и ищет границы gear-хешем:
   `fp = (fp << 1) + gear[байт]`, граница — там, где `fp & mask == 0`.
   До среднего размера используется «строгая» маска (на 2 бита больше),
   после — «мягкая» (на 2 бита меньше): это нормализация FastCDC уровня 2,
   она сжимает разброс размеров кусков вокруг среднего. Биты масок
   разнесены по старшей половине слова, где gear-хеш перемешан лучше.
   Таблица gear строится из splitmix64 с фиксированным seed, поэтому
   нарезка одинакова на любой машине (это проверяют тесты).
2. Для каждого куска считается SHA-256. Если такой кусок уже есть в таблице
   `chunks`, он не пишется второй раз.
3. Новый кусок пробуется сжать. Сжатая версия берётся, только если она
   меньше хотя бы на 1/16 — иначе распаковка при чтении не окупается.
4. Кусок дописывается в активный pack-файл одной записью (`pwritev`:
   заголовок + данные).
5. После последнего куска строится манифест; id файла — SHA-256 всего
   содержимого (считается тем же проходом). Манифест тоже дописывается в
   pack, как запись типа 2.
6. `fsync` pack-файла, потом запись `+1` в журнал ссылок и его `fsync`.

### Пачки и потоки

Шаги 2–3 делаются пачками: чанкер копит до 64 кусков (или 4 МБ), потом
пул потоков параллельно считает SHA-256 и пробует сжатие каждого куска.
Запись в pack после этого идёт строго по порядку кусков в одном потоке,
поэтому pack-файл побайтно одинаков при любом числе потоков (это проверяет
`test_pool`). Дубли внутри одной пачки отсекаются при записи: второй
экземпляр видит, что кусок уже записан первым.

Пул — это `ks_pool_run(p, fn, ctx, n)`: вызвать `fn(ctx, i)` для
`i = 0..n-1` и дождаться всех. Рабочие потоки берут номера из общего
счётчика под мьютексом, главный поток работает вместе с ними. Новая порция работы
объявляется номером поколения под мьютексом, конец — условной переменной.

Если такой файл уже был (тот же id), шаги 4–5 не пишут ничего: файл
получает ещё одну ссылку.

## Формат на диске

```
КАТАЛОГ/
  FORMAT        "kusok store v1\n" — защита от чужого каталога
  LOCK          flock: эксклюзивный для записи, общий для чтения
  packs/
    00000001.pack
    00000002.pack ...
  refs.snap     снимок счётчиков ссылок
  refs.log      журнал изменений после снимка
```

### pack-файл

Заголовок 24 байта: магия `KUSOKPK1`, версия, номер файла, CRC32C заголовка.
Дальше записи:

| смещение | размер | поле |
|---:|---:|---|
| 0 | 4 | CRC32C байт [4..48) и всех данных |
| 4 | 1 | тип: 1 — кусок, 2 — манифест |
| 5 | 1 | кодек: 0 — как есть, 1 — LZ4-блок |
| 6 | 2 | резерв |
| 8 | 4 | slen — длина на диске |
| 12 | 4 | rlen — длина после распаковки |
| 16 | 32 | id = SHA-256 несжатых данных |
| 48 | slen | данные |

Pack-файлы, кроме последнего, не меняются никогда, поэтому их можно
бэкапить инкрементально и раздавать read-only.

### Индекс .idx

Когда pack закрывается (переход на новый), рядом атомарно пишется
`0000000N.idx`: магия `KUSOKIX1`, версия, номер pack, длина pack, число
записей и по 56 байт на запись (смещение, slen, rlen, тип, кодек, id),
в конце CRC32C всего файла. При открытии индекс читается вместо обхода
pack. Индекс проверяется целиком до того, как из него что-то возьмут:
CRC, номер и длина pack, записи идут подряд без дыр и кончаются ровно на
длине pack. Если что-то не сходится — индекса как будто нет, pack
обходится как раньше, а при открытии на запись индекс пересоздаётся.
Индекс последнего (открытого на запись) pack удаляется при открытии:
этот pack ещё будет расти.

Индекс не заменяет CRC записей: данные по-прежнему проверяются при
чтении и в fsck, поэтому порча внутри закрытого pack видна там, а не
при открытии (тест `damaged_sealed_pack` проверяет оба случая).

### Манифест

`"KSMF"`, `u32 n`, `u64 размер файла`, затем `n` раз `[32] id куска, u32 длина`.
При разборе проверяется всё: магия, что `n` сходится с длиной, что нет
кусков нулевой длины и длиннее максимума, что сумма длин равна размеру.
В памяти манифест хранит префиксные суммы, и `ks_mf_find` за `O(log n)`
находит кусок по смещению.

### Пакет export/import

```
"KUSOKBN1"  u32 версия  u32 0
'R' + запись в формате pack (48 байт заголовка + данные)   — сколько угодно
'T' + u64 n + n × (id файла, i64 ссылок) + u32 CRC32C       — один раз
'E'
```

`export` пишет все куски и манифесты, кроме тех, что перечислены в списке
«уже есть» (`kusok ids` на другой стороне), и таблицу файлов со ссылками.
`import` читает поток по записям и для каждой проверяет CRC, длины и
содержимое: SHA-256 для куска, разбор для манифеста. Записи, которые уже
есть в хранилище, пропускаются. Таблица файлов применяется только после
того, как все записи дошли и проверены, и только к файлам, у которых в
хранилище есть все куски; каждый новый файл получает одну ссылку.
Пакет, оборванный посередине, оставляет хранилище согласованным: лишние
куски без ссылок соберёт gc. Буферы растут только вместе с реально
прочитанными данными, поэтому заголовок с огромной длиной не заставит
выделить гигабайты (это нашёл `fuzz_bundle`).

### Журнал ссылок

`refs.log` — записи по 48 байт: CRC, операция (+1/−1), `seq`, id файла.
`refs.snap` — атомарно записанный (tmp → fsync → rename → fsync каталога)
снимок всех счётчиков с `seq` последней учтённой записи.

Счётчики отделены от pack-файлов намеренно: сборка мусора переписывает
pack-файлы и при этом не трогает ссылки, а изменение ссылки — это 48 байт
в журнал, а не перезапись чего-то большого.

## Почему сбой в любой момент безопасен

Порядок записи:

1. куски → манифест → **fsync pack** → запись в журнал → **fsync журнала**;
2. перед переходом на новый pack старый сначала синхронизируется;
3. новый pack создаётся с `O_EXCL`, и каталог синхронизируется.

Отсюда инварианты:

- **ссылка в журнале никогда не указывает на файл, которого нет на диске**:
  в журнал пишется только после fsync данных;
- **оборванный хвост последнего pack** (запись, у которой не сошёлся CRC
  или которая короче заявленной длины) — это незавершённая запись, на
  которую никто не ссылается. При открытии такой pack *запечатывается*:
  всё, что до хвоста, читается, хвост считается мусором и уйдёт при
  ближайшей сборке, а новые записи идут в новый pack. Мы сознательно не
  обрезаем файл: если «рваный хвост» на самом деле — одна испорченная
  запись в середине, обрезка уничтожила бы всё, что после неё;
- **оборванный журнал** проигрывается до последней целой записи с
  непрерывным `seq`, остальное отрезается;
- **сбой между записью снимка и обрезкой журнала** не даёт двойного счёта:
  при проигрывании пропускаются записи с `seq <= snap.seq`;
- **pack с одним заголовком** (упали сразу после создания) при открытии
  на запись удаляется.

Всё это проверяет `tests/test_recovery.c`: он записывает эталонное
хранилище, затем для 372 длин обрывает копию его файлов и проверяет, что
хранилище открывается, каждый файл со ссылкой читается побайтно верно, а
fsck чист.

### Повреждения, а не сбои

Испорченный байт в середине *запечатанного* pack — это уже не сбой, а
порча носителя. По умолчанию `kusok_open` проверяет CRC только последнего
pack (быстро), а `fsck` — всех записей и восстанавливает каждый файл
целиком, сверяя SHA-256 с id. Режим `salvage` открывает хранилище, пропуская
испорченные записи: файлы, где все куски целы, читаются, остальные fsck
помечает как сломанные.

## Сборка мусора

`kusok_gc(ks, min_garbage)`:

1. **mark**: обходим файлы с ненулевым счётчиком, помечаем их манифесты и
   все куски из манифестов;
2. для каждого pack считаем живые байты; жертвы — pack-файлы, где доля
   мусора (включая рваный хвост) не меньше порога;
3. если активный pack — жертва, переходим на новый;
4. **compact**: живые записи жертв копируются в активный pack
   (уже сжатыми — без перекодирования), обновляется индекс;
5. fsync нового pack, удаление жертв, fsync каталога;
6. снимок счётчиков без нулевых записей, журнал обрезается.

Если упасть до шага 5, на диске будут дубли записей — при открытии побеждает
первая найденная копия, а лишняя уйдёт при следующей сборке. Если упасть
после удаления части жертв — все живые записи уже лежат в синхронизированном
новом pack.

## Производительность и выбор решений

- **SHA-256** — самое медленное звено (≈250 МБ/с в C, ≈945 МБ/с с SHA-NI).
  Используется потому, что id должен быть криптографическим: иначе можно
  подобрать коллизию и подменить чужое вложение. Аппаратная версия
  выбирается при запуске через `cpuid`, тесты сверяют обе.
- **CRC32C** только для обнаружения порчи; с SSE4.2 — 4–5 ГБ/с.
- **LZ4-блок** выбран за скорость распаковки (≈1.5 ГБ/с): чтение с
  произвольного смещения распаковывает целый кусок. Формат совместим с
  настоящим lz4, это проверяет `scripts/interop_lz4.py`.
- **HC-режим** (уровни 2..12) ищет совпадения не по одной ячейке хеша, а
  по цепочке всех прошлых позиций с тем же хешем 4 байт (окно 64 KiB,
  `prev[]` хранит шаг назад). Число проверок — `1 << (уровень - 1)`.
  Ленивый выбор: если со следующей позиции совпадение длиннее, текущий
  байт уходит в литералы. Распаковщик тот же, формат тот же.
- **Хеш-таблица** с линейным пробированием и удалением со сдвигом назад
  (без «надгробий»), заполненность ≤ 0.7. Индекс на 1 млн кусков — около
  80 МБ памяти.
- **Кэш кусков** — LRU на `cache_chunks` распакованных кусков (по
  умолчанию 64): хеш-таблица id → слот и двусвязный список по давности.
  Последовательное чтение и Range-запросы браузера почти всегда
  попадают в кэш. Плюс кэш последнего манифеста.

## Привязка для Node.js

Объект `Kusok` в JS держит `kusok *` и мьютекс. Быстрые вызовы (`size`,
`ref`, `stat`, …) выполняются сразу в потоке JS. Долгие (`put`, `read`,
`gc`, `fsck`) становятся `napi_async_work`: работа идёт в пуле libuv под
мьютексом хранилища, а Promise разрешается уже в потоке JS. На время
задачи держатся ссылки на сам объект и на буфер с данными, чтобы сборщик
мусора JS их не забрал. `close()` при незавершённых промисах отвечает
`EBUSY`, а не закрывает хранилище из-под работающей задачи.

## HTTP-сервер

`kusok serve` — один поток и `poll()`. У каждого соединения свой буфер
входа и очередь выхода; запросы в одном соединении обрабатываются по
порядку (конвейер), большие ответы отдаются частями по 64 KiB по мере
готовности сокета, поэтому медленный клиент не держит остальных. PUT
читает тело потоком прямо в `kusok_put_write`; пока идёт одна запись,
вторая получает 503 с `Retry-After`, потому что писатель у хранилища
один. Разбор HTTP (`tools/http.c`) отделён от сокетов и проверяется
модульным тестом и фаззером.

## Ограничения и что дальше

- дескриптор снаружи однопоточный; для сервера — одна очередь записи на
  процесс;
- индекс в памяти целиком (около 80 байт на кусок); файлы `.idx` ускоряют
  открытие, но не уменьшают память;
- нарезка FastCDC однопоточная и ограничивает скорость записи сверху;
- только POSIX;
- дальнейшие шаги: подключить привязку в offix (см. INTEGRATION.md),
  нативная сборка под Windows.
