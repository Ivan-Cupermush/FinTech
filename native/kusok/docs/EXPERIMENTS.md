# Эксперименты

Все числа ниже получены 2 ноября 2026 года на виртуальной машине:
Intel Xeon 2.10 GHz, 4 vCPU, Linux 6.18, gcc 13, сборка `Release` (`-O2`).
Машина общая, поэтому скорость от запуска к запуску гуляет на 10–40%;
где разброс заметный, указан диапазон по нескольким запускам.

Воспроизвести:

```sh
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release && cmake --build build
./build/kusok-bench all                       # скорость, потоки, уровни, сценарии
scripts/bench_git.sh ПУТЬ_К_РЕПОЗИТОРИЮ 40    # настоящие данные
```

или `docker run --rm kusok kusok-bench`. Все синтетические данные строятся
из фиксированного seed, поэтому таблица экономии места воспроизводится
байт в байт на любой машине.

## 1. Скорость (один поток)

| операция | МБ/с |
|---|---:|
| SHA-256, переносимый C | 180–260 |
| SHA-256, инструкции SHA-NI | 930–945 |
| CRC32C, таблицы slicing-by-8 | 1440–1540 |
| CRC32C, инструкция SSE4.2 | 3670–4930 |
| FastCDC, нарезка (средний кусок 8 KiB) | 1570–1700 |
| LZ4-блок, сжатие текста | 310–360 |
| LZ4-блок, распаковка текста | 1420–1580 |
| `kusok put`: текст (нарезка + SHA-256 + сжатие) | 150–190 |
| `kusok put`: случайные данные | 175–220 |
| `kusok put`: повтор уже сохранённого (только хеши) | 385–450 |
| `kusok read`: текст | 160–470 |

Выводы:

- аппаратный SHA-256 быстрее переносимого в 3.6–5 раз, и всё равно это
  самое медленное звено записи. Повторная загрузка уже сохранённого файла
  упирается именно в него;
- запись текста ограничена сжатием (≈330 МБ/с) плюс хешем;
- для сервера offix/mesNation этого хватает: даже гигабитный канал
  (≈119 МБ/с) один поток записи kusok успевает принимать, а загрузки
  вложений там идут через сеть пользователей, которая заметно медленнее.

Отдельно, через CLI: чтение файла 80.9 МБ текста целиком (`kusok get`,
вместе с запуском процесса и построением индекса) — 0.22–0.26 с.

### Потоки, уровни сжатия, индекс, кэш

`./build/kusok-bench more`, та же машина (4 vCPU):

| запись 64 МБ текста | МБ/с |
|---|---:|
| 1 поток | 179 |
| 2 потока | 245 |
| 4 потока | 290 |
| 8 потоков | 260 |

Ускорение на 4 потоках — 1.6 раза, не 4: нарезка FastCDC и запись в pack
идут в одном потоке, параллельно считаются только SHA-256 и сжатие. На
8 потоках при 4 ядрах уже мешают переключения. id файла при любом числе
потоков одинаковый (бенчмарк это проверяет).

| уровень, куски 64 KiB текста | сжатие МБ/с | распаковка МБ/с | размер |
|---:|---:|---:|---:|
| 1 (быстрый) | 321 | 656 | 30.4% |
| 2 | 119 | 673 | 27.9% |
| 4 | 89 | 815 | 25.1% |
| 6 | 39 | 787 | 22.1% |
| 9 | 15 | 1121 | 20.2% |
| 12 | 13 | 929 | 20.2% |

Чем выше уровень, тем длиннее совпадения и тем быстрее распаковка. Для
хранилища, где файл пишется один раз и читается много, уровни 4–6 —
разумный выбор; выше 9 выигрыша почти нет.

| открытие: 4000 файлов, 62 МБ, pack по 4 МБ | мс |
|---|---:|
| по индексам `.idx` | 3.6 |
| обходом pack-файлов | 9.1 |

Разница здесь небольшая, потому что pack-файлы лежат в кэше страниц ОС
сразу после записи; на холодном диске обход читает заголовок каждой
записи по всему файлу, а индекс — один последовательный файл.

| кэш чтения, 20000 чтений по 4 KiB из 512 KiB файла | попадания | мкс на чтение |
|---:|---:|---:|
| 1 кусок | 1.4% | 24.0 |
| 16 кусков | 30.2% | 17.1 |
| 64 куска (по умолчанию) | 99.8% | 0.2 |
| 256 кусков | 99.8% | 0.2 |

Когда «горячая» часть файла помещается в кэш, чтение перестаёт
распаковывать куски и становится в сто раз быстрее.

## 2. Экономия места: синтетические сценарии из жизни offix

Три сценария, каждый моделирует то, что реально происходит в продукте:

- **версии документа** — документ базы знаний на 2 МБ, 40 версий; между
  версиями 5 правок по 20–220 байт: вставка, удаление или замена текста
  (вставка и удаление сдвигают всё, что дальше);
- **пересылки вложений** — 120 вложений от 30 КБ до 2 МБ (2/3 — «фото»,
  которые не сжимаются, 1/3 — документы), каждое переслано от 1 до 12 раз;
- **недельные CSV из 1С** — выгрузка KPI за 52 недели: каждую неделю
  добавляется 1500 строк и исправляются 20 старых значений, причём
  половина исправлений удлиняет значение на цифру и сдвигает всё дальше.

| сценарий | без kusok | блоки 8K | блоки 4K | FastCDC | kusok | экономия |
|---|---:|---:|---:|---:|---:|---:|
| версии документа | 80.0 | 57.7 | 57.4 | 4.2 | 1.7 | 47.9x |
| пересылки вложений | 348.0 | 120.4 | 120.4 | 120.4 | 97.4 | 3.6x |
| недельные CSV из 1С | 90.0 | 81.3 | 81.0 | 12.2 | 3.8 | 23.6x |
| всего | 518.0 | 259.4 | 258.9 | 136.8 | 102.8 | 5.0x |

(МБ; «блоки 8K/4K» — дедупликация кусками постоянной длины, «FastCDC» —
уникальные байты после нарезки по содержимому, «kusok» — настоящий размер
pack-файлов на диске, с заголовками и сжатием.)

Выводы:

- **нарезка по содержимому решает**: там, где правки сдвигают данные
  (версии, CSV), блоки постоянной длины почти ничего не дают (57.7 из 80 МБ),
  а FastCDC — в 14–19 раз меньше. Уменьшение блока с 8K до 4K фиксированную
  нарезку не спасает;
- для пересылок одинаковых файлов все три способа равны — там работает
  дедупликация целого файла, а разница до 97.4 МБ — это сжатие тех вложений,
  которые ещё не сжаты;
- сжатие поверх дедупликации даёт ещё 1.2–3.2 раза.

## 3. Настоящие данные: история репозитория FinTech (offix)

`scripts/bench_git.sh` берёт каждый коммит основной ветки, делает
`git archive` (tar всего проекта) и кладёт в хранилище целиком — так, как
если бы команда каждый раз загружала архив проекта заново. 35 коммитов
с 19.10.2026 по 02.11.2026:

| способ хранения | МБ | во сколько раз меньше |
|---|---:|---:|
| 35 tar-архивов как есть | 77.9 | 1.0x |
| каждый архив в gzip -6 | 19.2 | 4.0x |
| kusok, только дедупликация (8 KiB, `--no-compress`) | 41.0 | 1.9x |
| kusok, по умолчанию (8 KiB + сжатие) | 19.1 | 4.1x |
| kusok, средний кусок 4 KiB | 16.3 | 4.8x |
| kusok, средний кусок 2 KiB | 13.2 | 5.9x |

Это честно менее эффектный результат, чем в синтетике, и он интересен
причиной: в tar перед каждым файлом стоит заголовок 512 байт с временем
изменения, а `git archive` ставит туда время коммита. Значит, в каждой
версии меняется *каждый* заголовок, и куски, где он лежит, перестают
совпадать. Чем мельче кусок, тем меньше данных «заражает» каждый
изменившийся заголовок — отсюда рост с 4.1x до 5.9x. На вложениях offix
(документы, CSV, фото) такой проблемы нет; а для архивов разумно хранить
файлы по отдельности или подбирать меньший средний кусок — kusok позволяет
задать его опциями `--avg/--min/--max`.

Отдельно видно, что на одном архиве исходников сжатие кусками по 8 KiB
почти догоняет gzip целого файла — потеря от поштучного сжатия невелика,
а взамен появляется чтение с любого смещения без распаковки всего файла.
