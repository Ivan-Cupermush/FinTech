# Встраивание в offix и mesNation

## Зачем

**offix** (github.com/Ivan-Cupermush/FinTech) — платформа целей, задач и
общения для вузов и компаний; **mesNation** — мессенджер, из которого offix
вырос. На обоих серверах файлы хранятся «как есть»: каждое вложение — отдельный
файл на диске. Из-за этого:

- пересланное в пять чатов вложение занимает место пять раз;
- каждая новая версия положения, отчёта или выгрузки из 1С — полная копия,
  хотя изменилась пара строк;
- проверить, что файлы на диске не испортились, нечем;
- бэкап каждый раз копирует всё заново.

Сервер — небольшой VPS (1 CPU, 2 ГБ памяти, маленький диск), поэтому
место и надёжность хранения там важнее, чем на большом кластере.

kusok закрывает все четыре пункта: дедупликация по кускам, сжатие, fsck по
SHA-256 и неизменяемые pack-файлы, которые бэкапятся инкрементально
(запечатанный pack никогда не меняется — `rsync` перешлёт только новые).

## Где это в коде offix

`server/src/services/media.ts`:

- `keepOriginal()` сейчас делает `fs.copyFile(tmp, files/ab/<hex>.<ext>)` для
  видео, документов и прочих файлов; ключ хранится в `attachments.storage_key`;
- `remove(keys)` удаляет файлы, когда удаляют сообщение или вложение;
- `pathOf(key)` превращает ключ в путь, а маршрут
  `GET /api/v1/files/:id/raw` (`server/src/routes/files.ts`) отдаёт файл через
  `res.sendFile(..., { acceptRanges: true })` — браузер просит куски файла
  заголовком `Range` при перемотке видео и просмотре PDF.

Превью (`thumbs/`) и аватары (`avatars/`) — маленькие, уникальные и раздаются
nginx/`sendFile` напрямую; их переносить смысла нет.

## Где это в коде mesNation

`server/src/lib/uploads.ts`: каталоги `chat`, `tasks`, `notes`, `imports`,
`knowledge`, каждый файл под случайным именем `<время>-<hex>.<ext>`. Именно
здесь больше всего повторов: пересылки в чатах и повторные импорты.

## План

### Шаг 1. Через командную строку (без изменений в сборке сервера)

Новый ключ хранения: `kusok:<64 hex>`. Старые ключи `files/...` продолжают
работать — миграция не обязательна и может идти фоном.

| место | было | станет |
|---|---|---|
| `keepOriginal` | `fs.copyFile` | `kusok --json DIR put TMP` → id, ключ `kusok:<id>` |
| `remove` | `fs.unlink` | `kusok DIR rm <id>` (минус ссылка) |
| `/files/:id/raw` без Range | `sendFile` | поток `kusok DIR get <id> -` |
| `/files/:id/raw` с Range | `sendFile` | `kusok DIR cat <id> <смещение> <длина>`, ответ 206 |
| ночью | — | `kusok DIR gc 0.3`, потом `kusok DIR fsck` (код 3 → алерт) |

Это тот же приём, которым сервер уже вызывает `ffmpeg` через `execFile`.
Запись идёт через одну очередь на процесс, потому что хранилище допускает
одного писателя (`flock`).

Минусы этого шага, о которых надо знать:

- каждый вызов CLI открывает хранилище заново и строит индекс по заголовкам
  pack-файлов. Пока хранилище — единицы гигабайт, это миллисекунды; для
  больших объёмов нужен шаг 2;
- пока писатель держит эксклюзивную блокировку (время одного `put`),
  читатели ждут.

### Шаг 1½. Через `kusok serve` (без запуска процесса на запрос)

`kusok DIR serve 127.0.0.1:8090` держит хранилище открытым, и сервер offix
ходит в него обычным HTTP:

| место | запрос |
|---|---|
| `keepOriginal` | `PUT /f` с телом файла → `{"id": …}`, ключ `kusok:<id>` |
| `remove` | `DELETE /f/<id>` |
| `/files/:id/raw` | `GET /f/<id>` с тем же заголовком `Range`, ответ проксируется как есть (200/206/416) |
| ночью | `POST /gc?min=0.3`, потом `kusok DIR fsck` |

Сервер слушает только localhost, наружу его не открываем — права
проверяет offix, а kusok видит только id. Одновременная запись второго
файла получает 503 с `Retry-After`, поэтому очередь загрузок в offix
остаётся.

### Шаг 2. Привязка для Node.js (N-API)

Готова в `bindings/node` (сборка с `-DKUSOK_NODE=ON`). Один открытый
`Kusok` на процесс сервера, без запуска процессов и без HTTP:

```ts
import { Kusok } from 'kusok';
const ks = new Kusok(process.env.FILES_DIR!, { compress: 4 });

// keepOriginal
const { id } = await ks.putFile(tmpPath);
const storageKey = `kusok:${id}`;

// GET /api/v1/files/:id/raw с Range
const buf = await ks.read(id, start, end - start + 1);
res.status(206).set('Content-Range', `bytes ${start}-${end}/${ks.size(id)}`).send(buf);

// remove
ks.unref(id);
```

Промисы выполняются в пуле libuv, поэтому event loop сервера не стоит,
пока считается SHA-256 большого видео.

### Шаг 3. Миграция старых файлов

Фоновая задача: для каждой строки `attachments` с ключом `files/...` —
`put`, проверка, что SHA-256 совпал, замена ключа одной транзакцией,
удаление старого файла. Ошибка на любом шаге — строка остаётся со старым
ключом, ничего не теряется.

## Бэкап

Сейчас бэкап — копия каталога целиком. С kusok достаточно передавать
только новые куски:

```sh
kusok /backup/offix ids > have
ssh vps kusok /srv/files export - have | kusok /backup/offix import -
```

`import` проверяет SHA-256 каждого куска до того, как файл станет виден в
бэкапе.

Утилита годится, пока хранилище никто не держит на запись: читатель берёт
общую блокировку `flock`, а работающий сервер держит исключительную, и
`export` из второго процесса получает «store is locked». Поэтому в offix
копию снимает сам сервер через привязку — `ids()`, `exportTo(path, known)`
и `importFrom(path)` работают на том же открытом хранилище под тем же
мьютексом: `server/src/services/storage-jobs.ts`, функция `backupKusok`.

## Windows

mesNation умеет разворачиваться на Windows (`deploy/windows`). kusok сейчас
использует POSIX (`pwritev`, `flock`, `fsync` каталога), поэтому там он
работает через WSL. Нативный порт — это замена `fsutil.c` и блокировки
(`LockFileEx`, `FlushFileBuffers`); формат на диске от ОС не зависит.

## Что проверяет, что встраивание безопасно

- id файла — SHA-256 содержимого, сервер может сверить его сам;
- `kusok fsck` после каждой ночной сборки;
- тест восстановления после сбоя (`tests/test_recovery.c`) покрывает ровно
  ситуацию «сервер упал посреди загрузки»: незавершённая загрузка не
  оставляет ссылок и уходит при сборке мусора.
